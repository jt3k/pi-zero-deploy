# pizdeploy

Утилита командной строки для деплоя проекта на Raspberry Pi: собирает проект, упаковывает артефакты `dist`, вычисляет детерминированный хэш архива, атомарно разворачивает новую версию и **проверяет, что служба действительно работает**. Работает от имени обычного пользователя — привилегии суперпользователя на целевом хосте не нужны.

## Требования

- macOS / Linux (POSIX-оболочка).
- Рантайм [Bun](https://bun.sh) (1.4+) в `PATH`.
- Системные клиенты `ssh` и `scp` (OpenSSH) в `PATH`.
- Настроенный доступ по SSH-ключу к целевому устройству (`ssh-copy-id <user@host>`). Интерактивный ввод пароля не поддерживается (`BatchMode=yes`).
- Сборка проекта: команда `bun run build` (собирает артефакты в `dist/`) либо скрипт `scripts.start`, указывающий на входной JS/TS файл (в этом случае `pizdeploy` соберёт проект автоматически через `bun build`).
- На целевом хосте: `systemd` с пользовательским менеджером (`systemctl --user`) и Node.js по пути `/usr/bin/node`.

## Установка

```sh
bun install
bun link
```

`bun link` создаёт симлинк `~/.bun/bin/pizdeploy`. Каталог `~/.bun/bin` должен быть в `PATH`.

## Использование

```sh
# Деплой на хост по умолчанию (pi@zero.local)
pizdeploy

# Деплой с явным указанием хоста
pizdeploy --ssh pi@custom.local
pizdeploy --ssh=pi@custom.local

# Предварительный просмотр без реального деплоя
pizdeploy --dry-run
pizdeploy --dry-run --ssh pi@custom.local

# Инспекция статуса запущенных сервисов на целевом хосте
pizdeploy ps
pizdeploy ps --ssh pi@custom.local

# Остановка службы (по умолчанию — текущий проект)
pizdeploy stop
pizdeploy stop other-service

# Отключение автозапуска службы (по умолчанию — текущий проект)
pizdeploy disable
pizdeploy disable other-service
```

## Конвейер деплоя

Все удалённые операции выполняются от имени подключаемого пользователя. **Ни один шаг не использует `sudo` и не пишет в `/etc/systemd/system`.** Каждый шаг — отдельный SSH-вызов по переиспользованному соединению, и ненулевой код возврата любого значимого шага останавливает деплой.

1. **Сборка** — запускает `bun run build` в текущем каталоге (если скрипт `build` объявлен в `package.json`) либо автоматически собирает входной JS/TS файл из `scripts.start` через `bun build <entry> --target=node --outfile=./dist/<name>.mjs --minify`.
2. **Упаковка** — архивирует содержимое папки `dist/` в `dist.tar.gz`.
3. **Хэширование** — вычисляет SHA-256 от архива, берёт первые 5 символов (`<hash5>`).
4. **Доставка** — копирует архив через `scp` во временную буферную директорию `~/projects/<name>/incoming/dist.tar.gz`. Больше через этот буфер ничего не передаётся.
5. **Автозапуск сессии (linger)** — перед установкой юнита проверяется `loginctl show-user <user> --property=Linger`; если выключено, включается `loginctl enable-linger <user>` и состояние перепроверяется. Без этого служба умирает вместе с SSH-сессией. Действие идемпотентно и выполняется не чаще одного раза за деплой.
6. **Распаковка** — создаёт директорию релиза `~/projects/<name>/releases/<name>_<hash5>`, распаковывает архив туда и удаляет временный файл из `incoming/`. Симлинк `current` на этом шаге не трогается.
7. **Атомарное переключение** — `ln -sfn` + `mv -fT` переводят `current` на новую директорию.
8. **Установка юнита** — сгенерированный unit-файл записывается в `~/.config/systemd/user/<service>`, затем вызывается `systemctl --user daemon-reload` и служба запускается/перезапускается: `systemctl --user enable --now <service> && systemctl --user restart <service>`.
9. **Верификация** — деплой считается успешным только когда служба реально работает (см. ниже). При неуспехе `current` возвращается на предыдущий релиз, каталог нового релиза остаётся на диске, код возврата ненулевой.
10. **Ротация** — удаляет старые релизы из `releases/`, оставляя последние 3. Сбой ротации успех не отменяет — это единственный шаг, где ошибка не фатальна.
11. **Очистка** — удаляет локальный временный файл `dist.tar.gz`.

### Верификация и таймаут

`Type=simple` означает, что systemd считает службу `active` сразу после `fork`, ещё до прослушивания порта. Поэтому успех подтверждается дополнительно:

| Конфигурация | Условие успеха |
| --- | --- |
| задан `pizdeploy.port` | служба в состоянии `active` **и** порт слушается (`ss -tln`) |
| порт не задан | служба в состоянии `active` **и** счётчик `NRestarts` не вырос за выдержку 5 с |

Опрос идёт с интервалом 1 с, общий таймаут — **60 с**. Запас достаточный: на Raspberry Pi Zero прямой запуск `node` поднимает приложение за ~5 с (в отличие от тяжёлой обёртки npm, тратившей более 26 с).

При отказе в stderr выводится причина: неполученный `active`, непрослушиваемый порт (с списком портов, которые на хосте реально слушаются) или рост `NRestarts` как признак падающего приложения. При сбое первого деплоя симлинк `current` удаляется (исключая зацикливание), а при наличии предыдущего релиза — возвращается на него.

### Структура каталогов на хосте

```
~/projects/<name>/
├── incoming/                         ← временный буфер (пуст после завершения деплоя)
├── releases/                         ← хранилище версий проекта
│   ├── <name>_abc12/                 ← старый релиз (будет удалён при ротации)
│   ├── <name>_def34/                 ← предыдущий релиз
│   └── <name>_5fa9b/                 ← текущий активный релиз
└── current -> releases/<name>_5fa9b/ ← симлинк на активную версию
```

## Конфигурация проекта

Поля читаются из `package.json` текущего рабочего каталога:

```json
{
  "name": "my-project",
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js"
  },
  "pizdeploy": {
    "ssh": "pi@my-pi.local",
    "service": "my-app.service",
    "port": 1234
  }
}
```

### Адрес хоста

Приоритет источников:

1. Флаг `--ssh <user@host>` командной строки.
2. Поле `pizdeploy.ssh` в `package.json`.
3. Значение по умолчанию: `pi@zero.local`.

### `pizdeploy.service`

Имя systemd-юнита. По умолчанию берётся из `name` пакета (`app.service`, если имени нет). Суффикс `.service` добавляется автоматически.

### `pizdeploy.port`

Необязательное число — порт, который приложение должно слушать. Нужен только для верификации деплоя и для колонки `URL` в `ps`; утилита передаёт его в службу как `Environment="PORT=<port>"`.

- **Порт задан** — успех требует, чтобы порт реально слушался. Если по истечении таймаута его никто не слушает, деплой завершается ошибкой с указанием ожидаемого порта и списка прослушиваемых.
- **Порт не задан** — проверка прослушивания пропускается, успех определяется состоянием службы и выдержкой `NRestarts` (проверка отсутствия крашей и роста числа рестартов).

### Канон запуска

Для деплоя проект **обязан** объявлять непустой скрипт `scripts.start` в своём `package.json` (например, `"start": "node dist/index.js"`). Если скрипт отсутствует или пуст, утилита немедленно завершает работу с ошибкой до начала каких-либо действий на хосте:
```text
pizdeploy: в package.json отсутствует обязательный скрипт 'scripts.start'
```

Юнит запускает процесс напрямую через `ExecStart` (без `npm start`), адаптируя пути под распакованный каталог релиза (префикс `dist/` удаляется, бинарник `node` приводится к `/usr/bin/node`). Это исключает лишний оверхед медленного `npm` на слабом железе Pi Zero и не требует присутствия `package.json` внутри каталога релиза.

## Шаблон systemd-юнита (`systemd-unit.service`)

Утилита формирует unit-файл и сохраняет его на хосте в `~/.config/systemd/user/<service>.service`.

По умолчанию используется эталонный шаблон из корня `pizdeploy`:
```ini
[Unit]
Description=app
After=default.target

[Service]
Type=simple
Restart=always
RestartSec=2
Environment="NODE_ENV=production"

[Install]
WantedBy=default.target
```

### Инициализация шаблона в проекте (`pizdeploy init`)

Если вашему проекту требуются специфичные переменные окружения (например, токен Telegram-бота), дополнительные зависимости или особые настройки restart, подготовьте локальный файл `systemd-unit.service` одной командой:

```sh
pizdeploy init
```

Команда:
1. Проверяет наличие `package.json` в текущем каталоге (при отсутствии выводит понятное предупреждение).
2. Берёт имя проекта из `package.json` и создаёт предзаполненный `systemd-unit.service`.
3. Добавляет подсказки для переменных окружения (`# Environment="BOT_TOKEN=..."`).
4. Не перезаписывает файл, если он уже существует.

Вам **не нужно** вручную указывать `WorkingDirectory` и `ExecStart`: `pizdeploy` автоматически внедряет актуальные пути к релизу (`/home/pi/projects/<name>/current`) и команду запуска из `scripts.start` `package.json`.

Пример для Telegram-бота:
```ini
[Unit]
Description=My Telegram Bot
After=default.target

[Service]
Type=simple
Restart=always
RestartSec=2
Environment="NODE_ENV=production"
Environment="BOT_TOKEN=123456789:ABCdefGHIjklMNOpqrsTUVwxyz"

[Install]
WantedBy=default.target
```

При деплое этот шаблон будет дополнен актуальными строками:
```ini
WorkingDirectory=/home/pi/projects/tg-bot/current
ExecStart=/usr/bin/node index.js
```
и установлен на Pi под именем вашей службы (например, `tg-bot.service`). Старый каталог `systemd/` в проекте игнорируется.

Если в проекте нет `systemd-unit.service`, деплой (`pizdeploy`) не прерывается, а использует стандартный эталонный шаблон.

Настройка `sudo` без пароля для `systemctl` **не требуется**: все службы работают в пользовательском менеджере systemd.

## Инспекция сервисов (`pizdeploy ps`)

Команда `pizdeploy ps` опрашивает целевой хост без привилегий и выводит таблицу со всеми задеплоенными проектами:

```sh
pizdeploy ps
```

```text
┌───┬────────────────┬───────────────┬──────────┬────────────────────────┬──────┐
│   │ Project        │ Release       │ Status   │ URL                    │ PID  │
├───┼────────────────┼───────────────┼──────────┼────────────────────────┼──────┤
│ 0 │ my-app         │ my-app_ee3d8  │ running  │ http://zero.local:1234 │ 7915 │
│ 1 │ weather-bot    │ weather_a1b2c │ inactive │ -                      │ -    │
│ 2 │ fresh-skeleton │ -             │ inactive │ -                      │ -    │
└───┴────────────────┴───────────────┴──────────┴────────────────────────┴──────┘
```

Смысл колонок:

- **Project** — имя каталога в `~/projects`.
- **Release** — имя директории, на которую указывает симлинк `current`. Прочерк означает, что релиза нет вообще (каталог создан, но деплоя не было).
- **Status** — `running`, если процесс проекта активен (слушает порт или запущен в systemd), иначе `inactive`.
- **URL** — `http://<host>:<port>` для запущенных проектов со слушающим портом; кликабельна (`Cmd + Click`). Прочерк — порт неизвестен или процесс не слушает входящие соединения.
- **PID** — идентификатор активного процесса.

Три состояния различимы: проект без релиза (`Release` = `-`), релиз есть но не запущен (непустой `Release`, `Status` = `inactive`), и запущен (`Status` = `running` с URL и PID).

Сопоставление процесса с проектом строгое: рабочая директория должна совпадать с каталогом проекта или лежать внутри него, поэтому проекты с префиксными именами (`app` и `app-worker`) не перехватывают статус друг друга.

## Управление службами (`start`, `stop`, `restart`, `status`, `logs`, `disable`, `remove`)

Утилита поддерживает каноничный набор команд управления жизненным циклом службы на хосте:

- `pizdeploy start [name]` — запустить службу (`systemctl --user start <service>`).
- `pizdeploy stop [name]` — остановить службу (`systemctl --user stop <service>`).
- `pizdeploy restart [name]` — перезапустить службу (`systemctl --user restart <service>`).
- `pizdeploy status [name]` — посмотреть подробный статус systemd (`systemctl --user status <service>`).
- `pizdeploy logs [name]` — посмотреть последние 50 строк журнала службы (`journalctl --user -u <service> -n 50 --no-pager`).
- `pizdeploy disable [name]` — отключить автозапуск службы (`systemctl --user disable <service>`).
- `pizdeploy remove [name]` (или `pizdeploy rm [name]`) — полностью снять проект с обслуживания:
  1. Останавливает службу (`systemctl --user stop`).
  2. Отключает её автозапуск (`systemctl --user disable`).
  3. Удаляет unit-файл `~/.config/systemd/user/<service>.service` и вызывает `daemon-reload`.
  4. Удаляет активный симлинк `current` (`~/projects/<name>/current`).
  5. Проект перестаёт отображаться в таблице `pizdeploy ps`. Каталог проекта и история `releases/` сохраняются на хосте (при необходимости их можно очистить вручную).

Если аргумент `[name]` не передан, имя службы и проекта определяется из локального `package.json`:

1. `pizdeploy.service`
2. `<name>.service` (по имени пакета)
3. `app.service` (по умолчанию)

Суффикс `.service` добавляется автоматически, если он опущен (например, `pizdeploy restart my-app` перезапустит `my-app.service`).

Перед выполнением команд `start`, `stop`, `restart`, `disable` утилита проверяет наличие службы в пользовательском менеджере (`systemctl --user cat`). Если служба не найдена, выводится понятное сообщение об ошибке с кодом возврата `1`.

## Режим `--dry-run`

Утилита не запускает сборку и не выполняет никаких сетевых операций — только выводит план:

```
[Dry-Run] Будет запущен bun run build, вычислен хэш архива и развернут релиз в: /home/pi/projects/my-project/releases/my-project_mock5
[Dry-Run] Служба my-project.service (user-юнит): /usr/bin/node index.js в /home/pi/projects/my-project/current, проверка порта 1234
```

## Коды возврата

- `0` — служба развернута и её работоспособность подтверждена.
- `1` — служба не найдена на хосте, либо верификация деплоя не пройдена (в этом случае `current` возвращён на предыдущий релиз).
- `2` — ошибка использования CLI (неизвестный флаг/аргумент или отсутствие значения флага `--ssh`).
- `127` — отсутствует `ssh` или `scp` в `PATH`.
- Иной ненулевой код — код завершения шага конвейера.

## Тесты

```sh
bun test
```

Тесты полностью изолированы от сети: `ssh`, `scp` и удалённый «хост» подменяются заглушками в песочнице во временном каталоге. Таймауты верификации в тестах переопределяются переменными окружения `PIZDEPLOY_VERIFY_TIMEOUT_MS`, `PIZDEPLOY_VERIFY_INTERVAL_MS`, `PIZDEPLOY_STABLE_HOLD_MS` — в бою они не используются.
