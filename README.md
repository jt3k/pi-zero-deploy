# pizdeploy

Утилита командной строки для деплоя проекта на Raspberry Pi: собирает проект, упаковывает артефакты `dist`, вычисляет детерминированный хэш архива и атомарно разворачивает новую версию на целевом хосте.

## Требования

- macOS / Linux (POSIX-оболочка).
- Рантайм [Bun](https://bun.sh) (1.4+) в `PATH`.
- Системные клиенты `ssh` и `scp` (OpenSSH) в `PATH`.
- Настроенный доступ по SSH-ключу к целевому устройству (`ssh-copy-id <user@host>`). Интерактивный ввод пароля не поддерживается (`BatchMode=yes`).
- Команда `bun run build` настроена в проекте и собирает артефакты в папку `dist/`.

## Установка

```sh
bun install
bun link
```

`bun link` создаёт симлинк `~/.bun/bin/pizdeploy`. Каталог `~/.bun/bin` должен быть в `PATH`.

## Использование

```sh
# Деплой на хост по умолчанию (pi@zero.local)
pizdeploy

# Деплой с явным указанием хоста
pizdeploy --ssh pi@custom.local
pizdeploy --ssh=pi@custom.local

# Предварительный просмотр без реального деплоя
pizdeploy --dry-run
pizdeploy --dry-run --ssh pi@custom.local

# Инспекция статуса запущенных сервисов на целевом хосте
pizdeploy ps
pizdeploy ps --ssh pi@custom.local

# Остановка службы (по умолчанию — текущий проект)
pizdeploy stop
pizdeploy stop other-service

# Отключение автозапуска службы (по умолчанию — текущий проект)
pizdeploy disable
pizdeploy disable other-service
```

## Конвейер деплоя

При каждом запуске pizdeploy выполняет следующие шаги:

1. **Сборка** — запускает `bun run build` в текущем каталоге.
2. **Упаковка** — архивирует содержимое папки `dist/` в `dist.tar.gz`.
3. **Хэширование** — вычисляет SHA-256 от архива, берёт первые 5 символов (`<hash5>`).
4. **Доставка** — копирует архив через `scp` во временную буферную директорию `~/projects/<name>/incoming/dist.tar.gz`.
5. **Распаковка** — создаёт директорию релиза `~/projects/<name>/releases/<name>_<hash5>`, распаковывает архив туда и удаляет временный файл из `incoming/`.
6. **Установка юнита** — если в репозитории есть `systemd/<service>`, обновляет его в `/etc/systemd/system/<service>` на Pi.
7. **Атомарное переключение** — переключает симлинк `current` на новую директорию в `releases/`, затем `daemon-reload` → `enable` → `restart`.
8. **Ротация** — удаляет старые релизы из `releases/`, оставляя последние 3.
9. **Очистка** — удаляет локальный временный файл `dist.tar.gz`.

### Структура каталогов на хосте

```
~/projects/<name>/
├── incoming/                         ← временный буфер (пуст после завершения деплоя)
├── releases/                         ← хранилище версий проекта
│   ├── <name>_abc12/                 ← старый релиз (будет удалён при ротации)
│   ├── <name>_def34/                 ← предыдущий релиз
│   └── <name>_5fa9b/                 ← текущий активный релиз
└── current -> releases/<name>_5fa9b/ ← симлинк на активную версию
```

## Приоритет разрешения адреса хоста

1. Флаг `--ssh <user@host>` командной строки.
2. Поле `pizdeploy.ssh` в файле `package.json` текущего рабочего каталога.
3. Значение по умолчанию: `pi@zero.local`.

Пример конфигурации в пользовательском `package.json`:
```json
{
  "name": "my-project",
  "scripts": {
    "build": "tsc"
  },
  "pizdeploy": {
    "ssh": "pi@my-pi.local",
    "service": "my-app.service"
  }
}
```

Поле `pizdeploy.service` задаёт имя systemd-сервиса (по умолчанию `app.service`).

## systemd-юнит

В репозитории находится файл [`systemd/app.service`](systemd/app.service) — шаблон юнита systemd. При каждом деплое он автоматически копируется на Raspberry Pi в `/etc/systemd/system/<service>`.

Отредактируйте его под свой проект:

```ini
[Service]
WorkingDirectory=/home/pi/projects/<name>/current
ExecStart=/usr/bin/node /home/pi/projects/<name>/current/server.js
```

Имя файла юнита определяется полем `pizdeploy.service` в `package.json` (по умолчанию `app.service`).

**Первый деплой** автоматически:
- копирует юнит в `/etc/systemd/system/`
- запускает `systemctl enable` (автозапуск при загрузке Pi)
- запускает `systemctl restart`

**Последующие деплои** обновляют юнит и делают `daemon-reload` — изменения в `.service` файле попадают на сервер как часть релиза.

> **Требуется:** `sudo` без пароля для команд `systemctl` на Raspberry Pi:
> ```sh
> echo 'pi ALL=(ALL) NOPASSWD: /bin/systemctl' | sudo tee /etc/sudoers.d/pi-systemctl
> ```



В режиме `--dry-run` утилита не запускает сборку и не выполняет никаких сетевых операций — только выводит путь планируемого развёртывания:

```
[Dry-Run] Будет запущен bun run build, вычислен хэш архива и развернут релиз в: /home/pi/projects/my-project/releases/my-project_mock5
```

## Инспекция сервисов (`pizdeploy ps`)

Команда `pizdeploy ps` быстро опрашивает целевой хост без необходимости прав `sudo` и выводит аккуратную таблицу со всеми задеплоенными проектами и их состоянием в реальном времени:

```sh
pizdeploy ps
```

Пример вывода:

```text
┌───┬─────────────────────┬─────────────────┬──────────┬────────────────────────┬─────────────────────────────┬──────┐
│   │ Project             │ Release         │ Status   │ URL                    │ Service                     │ PID  │
├───┼─────────────────────┼─────────────────┼──────────┼────────────────────────┼─────────────────────────────┼──────┤
│ 0 │ my-app              │ my-app_ee3d8    │ running  │ http://zero.local:1234 │ my-app.service              │ 7915 │
│ 1 │ weather-bot         │ weather_a1b2c   │ inactive │ -                      │ -                           │ -    │
└───┴─────────────────────┴─────────────────┴──────────┴────────────────────────┴─────────────────────────────┴──────┘
```

- **URL:** кликабельная ссылка (`Cmd + Click` в современных терминалах) для сервисов, слушающих сетевой порт.
- **Service & PID:** имя службы systemd и идентификатор процесса, полученные напрямую из ядра Linux (`/proc`).

## Управление службами (`pizdeploy stop` и `pizdeploy disable`)

Подкоманды позволяют быстро управлять жизненным циклом служб на Raspberry Pi через SSH:

- `pizdeploy stop [name]` — выполняет `sudo systemctl stop <service>` на удалённом хосте.
- `pizdeploy disable [name]` — выполняет `sudo systemctl disable <service>` на удалённом хосте.

Если аргумент `[name]` не передан, имя службы автоматически определяется из локального `package.json` текущей папки:
1. `pizdeploy.service`
2. `<name>.service` (по имени пакета)
3. `app.service` (по умолчанию)

Суффикс `.service` добавляется автоматически, если он опущен (например, `pizdeploy stop my-app` остановит `my-app.service`).

Перед выполнением команды утилита проверяет наличие службы на хосте. Если служба не найдена, выводится понятное сообщение об ошибке с кодом возврата `1`.

## Коды возврата

- `0` — успешное развёртывание на удалённом хосте.
- `2` — ошибка использования CLI (неизвестный флаг/аргумент или отсутствие значения флага `--ssh`).
- `127` — отсутствует `ssh` или `scp` в `PATH`.
- Ненулевой код — код завершения одной из команд в конвейере деплоя.
