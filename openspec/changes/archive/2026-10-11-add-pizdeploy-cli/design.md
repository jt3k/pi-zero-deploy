# Design

## Context

Проект инициализирован: `package.json` с `bin` и `src/index.ts` с `console.log("worked")` уже существуют. Мотивация — в `proposal.md`, требования — в `specs/cli-command/spec.md`.

Проверенное окружение разработки (macOS, zsh):

- Bun установлен: `~/.bun/bin/bun`, версия 1.4.0.
- `~/.bun/bin` уже присутствует в `PATH`, там же лежат симлинки других CLI (`openspec`, `koda`), установленных через менеджер глобальных пакетов. Это готовый и уже принятый на машине способ публикации локальной команды.

## Goals / Non-Goals

**Goals:**

- Одна точка входа `pizdeploy`, которая гарантированно исполняет код проекта через Bun.
- Понятная диагностика при отсутствии Bun (а не системная ошибка оболочки).
- Нулевая сборка: правка исходника сразу видна при следующем запуске команды.
- Установка/удаление команды одной командой без `sudo`.

**Non-Goals:**

- Парсинг аргументов, субкоманды, флаги (`--help`, `--version`): аргументы передаются скрипту как есть и игнорируются им, вывод не зависит от них.
- Кроссплатформенность кроме macOS-оболочек (zsh/bash); Windows не поддерживается.
- Публикация пакета в реестр, CI/CD, автообновление.
- Распространение Bun или его установка из утилиты.

## Decisions

### D1. Двухслойный вход: shell-обёртка → Bun → скрипт проекта

`bin/pizdeploy` — POSIX-совместимый shell-скрипт (`#!/bin/sh`), который:

1. Резолвит **реальный путь** собственного файла с разворачиванием симлинков (цикл по `readlink`, либо `CDPATH= cd -P "$(dirname "$target")"`), и берёт каталог проекта как `dirname` от него. Это критично: `bun link` публикует команду симлинком в `~/.bun/bin`, поэтому наивный `dirname "$0"` указал бы на `~/.bun/bin`, а не на каталог проекта, и скрипт утилиты не нашёлся бы.
2. Проверяет `command -v bun`; при отсутствии пишет в stderr сообщение с явным указанием причины и команды установки (`curl -fsSL https://bun.sh/install | bash`) и завершается с кодом 127.
3. Иначе `exec bun "$root/src/index.ts" "$@"`.

`src/index.ts` — сам скрипт: `console.log("worked")` (Bun исполняет TypeScript нативно, сборка не нужна).

Почему не `#!/usr/bin/env bun` прямо в TS-файле: этот вариант короче, но при отсутствии Bun пользователь получает системное `env: bun: No such file or directory` без подсказки, а текст сообщения нам не контролируем — это плохо согласуется со сценарием «Bun отсутствует в PATH». Обёртка даёт контролируемую диагностику и единое место для будущей инициализации (логирование, версия Node-совместимости).

Почему не `bun build --compile` в нативный бинарник: противоречит требованию «исполнение делегируется рантайму Bun» и требует пересборки на каждую правку, что избыточно для локальной утилиты.

### D2. Публикация команды через `bun link`

В `package.json` задаются `"name": "pizdeploy"` и `"bin": { "pizdeploy": "bin/pizdeploy" }`; установка — `bun link` из каталога проекта, что создаёт симлинк `~/.bun/bin/pizdeploy`.

Альтернативы: `npm link` (тянет в проект npm/node-контур, хотя рантайм — Bun); ручной `ln -s` в `~/bin` (работает, но состояние не описано в `package.json` и его легко рассинхронизировать); `install(1)` в `/usr/local/bin` (требует `sudo`, нарушает требование об отсутствии root).

### D3. Вывод — ровно одна строка

Используется `console.log("worked")`: ровно одна строка с завершающим переводом, stdout без префиксов и логотипов, stderr не затрагивается. Это удовлетворяет сценариям «обычный запуск» и «вывод пригоден для конвейера».

### D4. Минимальный набор файлов

```
package.json      # name, version, type: module, bin
bin/pizdeploy     # shell-обёртка (executable)
src/index.ts      # логика вывода
README.md         # установка/проверка/удаление
```

Тесты — `bun test` с проверкой вывода дочернего процесса обёртки (см. `tasks.md`), без внешних тестовых библиотек: в проекте они не используются, а поведение полностью сводится к stdout/коду возврата.

## Risks / Trade-offs

- [`~/.bun/bin` отсутствует в `PATH` неинтерактивной оболочки — cron, CI, `sh -c`] → В README фиксируем альтернативу: запуск по полному пути `~/.bun/bin/pizdeploy`; обёртка сама не зависит от каталога вызова.
- [`bun link` создаёт симлинк: `dirname "$0"` указывает на `~/.bun/bin`, а не на проект] → Обёртка разворачивает симлинки до реального пути (шаг 1 в D1) и проверяет это тестом, запускающим команду через опубликованный симлинк.
- [`bun link` создаёт ссылку на конкретное имя пакета; переименование в `package.json` оставляет битую ссылку] → В README описываем переустановку (`bun unlink && bun link`) как единственный корректный путь после смены `name`.
- [Обёртка предполагает POSIX-оболочку и отсутствует на Windows] → Осознанное ограничение объёма (см. Non-Goals); зафиксировано в README.
- [Скрипт исполняется из исходников, а не из собранного артефакта: удаление или перемещение каталога проекта ломает команду] → Документируем, что проект — постоянное место установки; удаление выполняется осознанно через `bun unlink`.
- [Зависимость от внешнего Bun] → Проверяется на каждом запуске обёрткой; код отказа и текст подсказки заданы явно.

## Migration Plan

Установка: `cd ~/work/pizdeploy && bun install && bun link`, затем в новой сессии терминала `pizdeploy` → `worked`.

Откат: `bun unlink` (удаляет симлинк `~/.bun/bin/pizdeploy`), удаление файлов проекта. Системные каталоги не затрагиваются, `sudo` не требуется.
