# Design

## Context

Мотивация — в `proposal.md`. Здесь — только текущее состояние и ограничения, которые формируют решение.

Есть работающая двухслойная точка входа: `bin/pizdeploy` (POSIX-обёртка, резолвит симлинк `bun link`, проверяет Bun, `exec bun "$root/src/index.ts" "$@"`) и `src/index.ts` с `main(argv): number`. Обёртку менять не нужно — аргументы уже долетают до `main`.

Проверенное окружение разработки (macOS):

- `ssh` — `/usr/bin/ssh`, OpenSSH_8.6p1.
- Bun 1.4.0, `~/.bun/bin` в `PATH`.
- Доступ к `pi@zero.local` по ключу настроен (`ssh-copy-id`), интерактивный ввод пароля не требуется.
- Замер получения рабочего каталога: `process.cwd()` — ~0.04 мс/вызов, `` $`pwd`.text() `` — ~4 мс/вызов (спавн оболочки). Разница в ~100 раз, поэтому берётся `process.cwd()`.

Тесты в проекте — интеграционные: `test/cli.test.ts` запускает `bin/pizdeploy` как дочерний процесс и сверяет stdout/stderr/код возврата. Внешних зависимостей (в том числе тестовых библиотек) в `package.json` нет — `dependencies`/`devDependencies` отсутствуют полностью.

## Goals / Non-Goals

**Goals:**

- Одно место разрешения адреса с предсказуемым приоритетом источников.
- Удалённая команда формируется так, чтобы имя локального каталога не могло стать исполняемым кодом на сервере.
- Вывод и код возврата `ssh` доходят до пользователя без искажений — утилита ведёт себя как прозрачная обёртка.
- Тесты, которые не требуют живого сервера и сети.

**Non-Goals:**

- Свой SSH-транспорт, пул соединений, keepalive, параллельные хосты.
- Валидация адреса по формату `user@host` — проверяются только признаки небезопасного/бессмысленного значения (см. D4).
- Поддержка `--help`/`--version`, субкоманд, пресетов, `scp`/`rsync`.
- Изменение `bin/pizdeploy` и способа установки (`bun link`).

## Decisions

### D1. Системный `ssh` через Bun Shell, а не JS-библиотека

Удалённое выполнение — `` await $`${SSH} ${host} ${remoteCmd}` ``, где `SSH = "ssh"`. Bun Shell сам котирует подставляемые значения при сборке командной строки, а `ssh` на стороне клиента получает уже готовую строку команды, которую передаёт логину оболочки сервера.

Почему не `ssh2`/`node-ssh`: они отрывают нас от `~/.ssh/config`, `ProxyJump`, ssh-агента и `IdentityFile` — то есть от того, что у пользователя уже настроено и работает. Плюс это первая npm-зависимость в проекте, где их сейчас нет вовсе. Системный `ssh` сохраняет привычное поведение OpenSSH «бесплатно».

Почему не `Bun.spawn(["ssh", host, cmd])`: тоже рабочий вариант и он даёт прозрачный стриминг через `stdout: "inherit"`. Выбираю Bun Shell по требованию пользователя писать через `$`, а стриминг настраивается опциями `$` (`.stdout("inherit").stderr("inherit")`). Если окажется, что `.text()` буферизует вывод и ломает интерактивность — переход на `Bun.spawn` с `inherit` остаётся открытым, поведение из спеки от этого не меняется.

Пользователь явно отказался от проверки наличия `ssh` до запуска: путь не резолвится, `PATH` не инспектируется. Но «сообщение с кодом 127» требует различать «`ssh` нет» и «`ssh` есть, но упал». Bun Shell при отсутствующем бинарнике бросает исключение с `errno` `ENOENT` — его и ловим, печатаем своё сообщение про `ssh` и возвращаем 127. Это не «проверка заранее», а обработка уже случившейся ошибки, и она согласуется с требованием спеки.

### D2. Приоритет источников адреса — явная цепочка, а не слияние конфигов

```
resolveHost(argv, cwd):
  1. флаг --ssh из argv            (если задан — используется как есть, после trim)
  2. package.json.pizdeploy.ssh    (ближайший package.json от cwd вверх)
  3. DEFAULT_HOST = "pi@zero.local"
```

Значение считается «заданным» только если после `trim()` оно непустое. Пустая строка в `package.json` не перекрывает дефолт — иначе опечатка в конфиге молча ломает подключение. Флаг же перекрывает всё, даже если выглядит подозрительно: он проходит только проверку из D4.

Поиск `package.json`: от `process.cwd()` вверх до корня файловой системы, берётся первый найденный читаемый файл. Это повторяет семантику `npm`/`bun` и интуитивно для «проекта, из которого запустили команду». Читаем через `Bun.file(...).json()` в `try/catch`: битый JSON или отсутствие поля не ошибка, а «источник не дал значения».

Альтернатива — читать только `./package.json` без подъёма вверх: проще, но ломает сценарий «запустил из `src/`». Оставляю подъём.

### D3. Экранирование удалённой команды — одинарные кавычки POSIX

Удалённая команда: `echo 'pwd: <cwd>'`. Путь берётся из `process.cwd()` и подставляется в одинарные кавычки, а каждая одинарная кавычка внутри заменяется на `'\''` (закрытие кавычки, экранированная кавычка, открытие кавычки). Это канонический POSIX-приём, не требующий экранирования остальных символов: внутри одинарных кавычек `$`, `` ` ``, `;`, `|` теряют смысл.

Пример: `/tmp/it's` → `echo 'pwd: /tmp/it'\''s'`.

Почему не двойные кавычки: внутри них раскрываются `$` и обратные кавычки, то есть путь с `$(` превратился бы в выполнение кода на сервере. Почему не `JSON.stringify`: JSON-кавычки не совпадают с синтаксисом POSIX-оболочки.

Отдельная защита — адрес хоста. Значение, начинающееся с `-`, было бы принято `ssh` за опцию (например, `-oProxyCommand=...` = выполнение кода локально). Поэтому адрес, начинающийся после `trim()` с `-`, отвергается на этапе разбора с кодом 2 (см. требование «Ошибки использования завершаются кодом 2»).

### D4. Разбор аргументов — минимальный и строгий

Линейный проход по `argv`:

- `--ssh=<v>` → значение `v`; `--ssh <v>` → следующий токен, его отсутствие = ошибка использования.
- любой другой токен → ошибка использования.
- повторный `--ssh` → последнее значение побеждает, молча (дешевле, чем ветка ошибки, и не скрывает опечатку в выводе).

Ошибка использования = сообщение в stderr, начинающееся с `usage: pizdeploy [--ssh <user@host>]`, код возврата **2**. Двойка выбрана как соглашение `getopt`/`grep`/`diff` для ошибки использования и отличается от кодов, которые возвращает `ssh` (255 — ошибка подключения/транспорта), поэтому скрипты смогут их различать.

### D5. Подавление интерактивности: `-o BatchMode=yes -o ConnectTimeout=3`

Без этих опций запуск при незакрытом ключе зависает на запросе пароля (stdin у дочернего процесса — терминал), а недоступный по DNS `zero.local` висит до TCP-таймаута. Пользователь подтвердил, что доступ по ключу настроен, поэтому интерактивная аутентификация утилите не нужна вовсе.

- `BatchMode=yes` — `ssh` немедленно падает вместо запроса пароля/проходки.
- `ConnectTimeout=3` — короткая пауза на установку TCP-соединения: недоступный хост отсекается за 3 с, а не за дефолтный TCP-таймаут, и обычный успешный коннект в локальной сети этого времени не выбирает.

Обе опции передаются как аргументы `ssh` до хоста и не мешают `~/.ssh/config` (конфиг по-прежнему задаёт пользователя, порт, jump-хосты). Альтернатива `</dev/null` — перекрывает stdin, но не спасает от зависания на DNS и менее явна.

### D6. Тесты без живого сервера — подмена `ssh` в `PATH`

Живой `pi@zero.local` в тестах недопустим (сеть, внешний хост, невозможность проверить отрицательные сценарии). Тестовая harness создаёт временный каталог, кладёт в него исполняемый скрипт `ssh`, который печатает полученные аргументы по одному на строку (или эмулирует заданный код возврата через переменную окружения), и запускает `bin/pizdeploy` с `PATH = <этот каталог>:<каталог bun>`. Так проверяются: выбранный хост, буквально сформированная удалённая команда, экранирование кавычки и пробела, коды 2/127.

Для сценария «`ssh` отсутствует» используется `PATH`, содержащий только каталог с симлинком на `bun` (`process.execPath`) — `ssh` там взяться неоткуда. Существующий тест «нет Bun в PATH» (`PATH=/usr/bin:/bin`) сохраняется без изменений: там `ssh` есть в `/usr/bin`, но до него не доходит.

## Risks / Trade-offs

- [Удалённая сторона может использовать не POSIX-оболочку (csh/tcsh на сервере) — `'\''` не сработает] → Целевая Raspberry Pi — Linux с `bash`/`dash`; фиксируем как ограничение в README. Сценарий с кавычкой в имени каталога проверяется тестом на стороне сформированной строки, а не живым сервером.
- [`BatchMode=yes` ломает сценарий парольной аутентификации] → Осознано: утилита рассчитывает на ключи, это задокументировано в README; зависание CLI хуже, чем явный отказ.
- [Подмена `ssh` в `PATH` в тестах может разойтись с реальным поведением OpenSSH] → Тесты проверяют только наш контракт (какие аргументы мы передали), а не поведение `ssh`; реальный канал покрывается ручной проверкой из `tasks.md`.
- [Поиск `package.json` вверх по дереву может подобрать чужой конфиг] → Риск принят ради работы из подкаталогов; приоритет флага позволяет всегда переопределить результат явно.
- [`.text()` в Bun Shell буферизует вывод — длинные удалённые команды не показывают прогресс] → Для `echo` незаметно; зафиксировано в D1 как точка перехода на `Bun.spawn` + `inherit`, если понадобится.
- [Код 2 может совпасть с кодом, который вернула удалённая команда] → Ошибки использования возвращаются до запуска `ssh`, поэтому 2 от нас означает именно ошибку разбора; различие документировано в README.

## Migration Plan

1. Реализация в `src/index.ts`, обновление `test/cli.test.ts`, обновление `README.md`.
2. Проверка: `bun test`, затем ручные сценарии (`pizdeploy`, `pizdeploy --ssh ...`, ошибка использования, отсутствие `ssh`).
3. Откат: изменение локализовано в `src/index.ts` + тестах + README, внешних зависимостей нет — `git revert` возвращает заглушку `worked` без побочных эффектов.
