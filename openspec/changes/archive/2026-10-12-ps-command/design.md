# Design

## Context

Утилита `pizdeploy` развёртывает проекты на Raspberry Pi в каталоги `/home/pi/projects/<name>/` с переключением симлинка `current`. См. `proposal.md` - Why.
Для удалённого выполнения используется OpenSSH клиент с мультиплексированием соединений (`ControlMaster`). На целевой микро-ноде (Raspberry Pi OS) ресурсы процессора и накопителя ограничены, поэтому сбор информации должен быть максимально быстрым, без сканирования всего диска и без прав `sudo`.

## Goals / Non-Goals

**Goals:**
- Предоставить команду `pizdeploy ps`, которая за один SSH-вызов собирает состояние всех задеплоенных проектов на целевой ноде.
- Отображать имя проекта, текущий релиз, статус службы (`running`/`inactive`), имя systemd-юнита, PID и кликабельный веб-адрес `http://<host>:<port>`.
- Использовать встроенный метод Bun `console.table()` без привлечения сторонних библиотек форматирования терминала.

**Non-Goals:**
- Интерактивный TUI/дашборд в реальном времени (аналог `htop` или `k9s`).
- Просмотр журналов и логов (`journalctl`).
- Управление жизненным циклом сервисов (`stop`/`restart`) из команды `ps` — для этого используются деплой и стандартные системные команды.

## Decisions

### 1. Ядро Linux (`/proc`) и `ss` как единственный источник истины

- **Выбор:** Собирать динамическое состояние на лету через `/proc/<pid>/cwd`, `/proc/<pid>/cgroup` и утилиту сокетов `ss -tlpn`.
- **Альтернативы:**
  - *Статический манифест `.pizdeploy.json` на сервере*: отклонен, так как статический файл становится невалидным после перезагрузки ОС, падения процесса или внешней остановки службы.
  - *Полный опрос `systemctl show '*'`*: отклонен из-за высокой нагрузки на одноядерный CPU Pi Zero (парсинг сотен юнитов занимает секунды).
- **Обоснование:** Симлинк `/proc/<pid>/cwd` ядра Linux прямо указывает на рабочий каталог релиза, а `/proc/<pid>/cgroup` содержит имя юнита systemd. Запрос выполняется за миллисекунды в RAM ядра и не требует прав суперпользователя.

### 2. Сбор данных через однострочный сборщик с выводом в JSON

- **Выбор:** Удалённая команда запускает компактный сборщик (Python 3, встроенный в стандартную поставку Raspberry Pi OS), который связывает `ss -tlpn` и `/proc`, инспектирует `~/projects/*` и возвращает структурированный JSON в stdout.
- **Альтернативы:**
  - *Парсинг bash-пайпами в shell*: сложнее безопасно экранировать пути и имена, хрупкий вывод.
- **Обоснование:** Python 3 предустановлен в стандартном образе Raspberry Pi OS (Debian), надёжно формирует JSON за один процесс (~0.2 сек) и исключает ошибки парсинга.

### 3. Отрисовка через встроенный API Bun `console.table()`

- **Выбор:** Локальный процесс `pizdeploy` парсит полученный JSON и передаёт нормализованный массив объектов в `console.table()`.
- **Альтернативы:**
  - *Сторонние npm-библиотеки (cli-table3, chalk)*: лишний вес и зависимости.
  - *Самописное вычисление ширины колонок*: дублирование функционала.
- **Обоснование:** `console.table()` встроен в Bun из коробки, генерирует аккуратную таблицу в UTF-8/ASCII и автоматически выравнивает заголовки и ячейки.

### 4. Генерация кликабельных URL

- **Выбор:** Адрес формируется как `http://${hostname}:${port}`, где `hostname` извлекается из адреса подключения (отсекая `user@`).
- **Обоснование:** Терминалы (iTerm2, VS Code, Alacritty, Ghostty) распознают стандартную структуру URL и позволяют открывать веб-сервис в браузере по обычному клику (Cmd+Click).

## Risks / Trade-offs

- **[Минималистичный образ без python3]** → Если на целевом хосте установлена урезанная кастомная ОС без Python, команда вернет код ошибки. *Митигация:* предусмотреть обработку ошибки или альтернативную легковесную команду shell.
- **[Привязка сервиса к localhost (127.0.0.1)]** → Сервис может слушать только локальный интерфейс малинки, поэтому ссылка `http://zero.local:<port>` не откроется в браузере на машине разработчика без туннеля. *Митигация:* отображать порт как есть, это естественное сетевое поведение.
