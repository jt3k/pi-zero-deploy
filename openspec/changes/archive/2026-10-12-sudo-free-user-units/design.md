# Design

## Context

Замеры на целевом хосте (`pi@zero.local`, Raspberry Pi Zero, Node 20.19.2, systemd 257):

- `sudo` для пользователя `pi` требует пароль; в NOPASSWD только `/usr/bin/systemctl` и `mv /tmp/* /etc/systemd/system/*`. `sudo cp` в `/etc/systemd/system` недоступен, интерактивный ввод исключён (`BatchMode=yes`).
- Путь без root подтверждён экспериментом: `loginctl enable-linger pi` → rc=0, `Linger=yes`; юнит в `~/.config/systemd/user/` → `systemctl --user enable --now` → `active`, порт слушается, HTTP 200. `~/.config/systemd/user/` до этого не существовал, `Linger` был `no` — то есть user-менеджер на хосте ещё никто не использовал.
- `ExecStart=/usr/bin/npm start` с `WorkingDirectory=<project>/current` поднимает приложение. `MainPID` — это `npm`, слушает дочерний `node`, его `cwd` = каталог релиза (симлинк разрешается).
- Время от старта до прослушивания порта на Pi Zero: **~45–60 с** (npm-обёртка очень медленная). Любая проверка с коротким таймаутом даст ложный отказ.
- Путь cgroup user-юнита: `0::/user.slice/user-1000.slice/user@1000.service/app.slice/<name>.service`. Текущая регулярка с `head -n1` возвращает `user@1000.service` — имя проекта теряется.
- Хвостовой `|| true` в `&&`-цепочке обнуляет код возврата всей цепочки: `false && B && (C || true)` → 0. Это и есть причина `🎉` при мёртвом `sudo`.
- `journalctl --user` на хосте ответил «No journal files were found». Это наблюдение сделано, когда на хосте не было ни одного проработавшего и ни одного упавшего user-юнита, поэтому вывод о доступности journal для user-служб сделать нельзя. Никаких утверждений о логах и диагностике падений это изменение не содержит.

## Goals / Non-Goals

**Goals:**

- Ни одного `sudo` в удалённых командах утилиты.
- Деплой завершается успехом только когда служба реально работает.
- `npm start` — единственный канон запуска; имена артефактов сборки нигде не фигурируют.
- `ps` корректно показывает user-юниты и различает «нет релиза» / «есть релиз, не запущен» / «работает».

**Non-Goals:**

- Управление system-юнитами (`/etc/systemd/system`) не поддерживается вообще.
- Отдельной команды миграции как подкоманды CLI не вводится — очистка выполняется одноразово вручную по списку из Migration Plan.
- Диагностика падений и вывод логов служб в объём этого изменения не входят: на хосте ещё не было ни одного проработавшего и ни одного упавшего user-юнита, поэтому утверждать что-либо о доступности journal для user-служб преждевременно.
- Порты и хосты по умолчанию (`pi@zero.local`) не меняются.

## Decisions

### 1. User-менеджер systemd вместо system-юнитов

`systemctl --user` + `~/.config/systemd/user/<service>`. Альтернатива — просить администратора добавить `sudo cp` в NOPASSWD: отклонено, потому что делает утилиту зависимой от ручной настройки конкретного хоста и не решает проблему автозапуска после перезагрузки без `enable` под root. `nohup`/`setsid`-подход отклонён: нет перезапуска при падении и нет переживания перезагрузки.

Linger включается лениво — перед первой установкой юнита, а не при каждом запуске: `loginctl enable-linger <user>` идемпотентен и не требует root для собственного пользователя.

### 2. Юнит генерируется, а не копируется

Каталог `systemd/` в деплоящем проекте упраздняется. Шаблон:

```
[Unit]
Description=<name>
After=default.target

[Service]
Type=simple
WorkingDirectory=/home/pi/projects/<name>/current
ExecStart=/usr/bin/npm start
Restart=always
RestartSec=2
Environment="NODE_ENV=production"
[Install]
WantedBy=default.target
```

`WantedBy=default.target` (не `multi-user.target`) — в user-менеджере последнего нет. `KillMode` остаётся значением по умолчанию (`control-group`), поэтому при остановке systemd добивает дочерний `node` вместе с `npm`-обёрткой. `PORT` добавляется как `Environment`, только когда задан `pizdeploy.port`.

Альтернатива `ExecStart=/usr/bin/node <entry>` отклонена: требует согласованного имени артефакта, что и стало причиной исходного сбоя (`server.js` vs `app.js`).

### 3. Верификация: состояние + порт, с большим таймаутом

`Type=simple` означает, что systemd считает службу `active` сразу после `fork`, до прослушивания порта. Поэтому:

- если `pizdeploy.port` задан — успех = `is-active` **и** порт слушается; опрос с интервалом, общий таймаут **180 с** (запас от измеренных 60 с);
- если порт не задан — успех = `is-active` **и** `NRestarts` не вырос за выдержку 20 с.

Отказ → ненулевой код, `current` возвращается на предыдущий релиз; каталог нового релиза при этом не удаляется.

### 4. Удалённые шаги — отдельные вызовы вместо одной `&&`-цепочки

Каждый значимый шаг (распаковка, переключение `current`, запись юнита, `daemon-reload`, `enable --now`, верификация, ротация) выполняется отдельным `ssh`-вызовом по уже открытому ControlMaster-сокету и проверяется на `exitCode !== 0`. `|| true` допускается только внутри шага, который по контракту не может быть фатальным (ротация), и не может повлиять на чужой код возврата. Один лишний round-trip на Pi Zero — десятки миллисекунд по переиспользованному соединению; цена приемлемая.

### 5. Имя службы в `ps` — последнее совпадение cgroup

`grep -oE "[^/]+\.service" | tail -n1`. Для system-юнита путь `/system.slice/<name>.service` даёт тот же результат, что и раньше, так что регрессии нет.

### 6. Конфигурация проекта

`pizdeploy.port` — необязательное число для проверки прослушивания. Поле `pizdeploy.service` сохраняет силу (имя юнита), каталог `systemd/` игнорируется.

## Risks / Trade-offs

- [Приложение слушает не тот порт, что в `pizdeploy.port`] → деплой честно падает; сообщение содержит ожидаемый и фактический списки портов из `ss`.
- [`npm start` не пробрасывает SIGTERM дочернему процессу] → `KillMode=control-group` по умолчанию добивает всю cgroup; при остановке дополнительно проверяется, что порт освободился.
- [Linger включается как побочный эффект деплоя] → действие идемпотентно и ограничено собственным пользователем; факт включения выводится в лог явной строкой.
- [Отказ верификации оставляет каталог нового релиза на диске] → ротация удалит его при следующем успешном деплое.
- [Очистка удаляет данные безвозвратно] → выполняется только по явному списку и только после того, как новый путь подтверждён на тестовом проекте.
- [Pi Zero, 180-секундный таймаут] → деплой стал заметно медленнее прежнего «сразу 🎉»; это осознанный обмен лжи на правду.

## Migration Plan

1. Реализовать и проверить конвейер на одноразовом тестовом проекте (`piztest`), не затрагивая существующие.
2. Задеплоить `pi-zero-deploy-lite` новым путём, убедиться что `http://zero.local:1234/` отвечает.
3. Только после шага 2 — разовая очистка неканоничного наследия (все операции без `sudo` там, где это возможно; удаление system-юнитов требует привилегий и выполняется вручную оператором):
   - `~/.config/systemd/user/pizprobe.service`, `piztest.service` — уже удалены экспериментом;
   - `/home/pi/projects/piztest` — уже удалён;
   - `/home/pi/projects/bench` — пустой скелет без релиза и без юнита, удалить каталог;
   - `/home/pi/projects/my-app` — юнита нет вообще, удалить каталог;
   - `/home/pi/projects/pi-zero-deploy-lite` — старые релизы с timestamp (`20261008*`) удалить после успешного деплоя; `/etc/systemd/system/pi-zero-deploy-lite.service` удалить вручную (нужны привилегии);
   - `/home/pi/projects/pi-zero-deploy` и `/etc/systemd/system/pi-zero-deploy.service` — тестовый юнит на `:3333`, больше не нужен: остановить, удалить каталог проекта и system-юнит (юнит — вручную, нужны привилегии).
4. Откат изменения: вернуть `src/index.ts` к предыдущей ревизии; user-юниты удаляются командой `systemctl --user disable --now <service>` и удалением файла.
