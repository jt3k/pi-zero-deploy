# Proposal

## Why

Сейчас `pizdeploy` устанавливает systemd-юнит в `/etc/systemd/system/` через `sudo cp`, что на целевом хосте невозможно без пароля (`BatchMode=yes` исключает интерактивный ввод). Деплой при этом завершается с кодом 0 и печатает `🎉`, потому что хвостовой `|| true` в шаге ротации обнуляет код возврата всей `&&`-цепочки: артефакт доставлен, `current` переключён, а служба никогда не запускалась. Проверено на проде — `NRestarts=269`, порт не слушается, при этом CLI рапортует об успехе.

Проверенный на том же хосте путь без root: `loginctl enable-linger` для собственного пользователя и `systemctl --user` с юнитом в `~/.config/systemd/user/` отрабатывают полностью без `sudo` (`active`, порт слушается, HTTP 200).

## What Changes

- **Переход на user-менеджер systemd (BREAKING).** Службы разворачиваются и управляются через `systemctl --user` и юниты в `~/.config/systemd/user/`. `sudo` не используется ни для одной операции.
- **Автовключение linger.** Перед первым установочным деплоем утилита включает `loginctl enable-linger <user>` для пользователя подключения, чтобы служба жила после разрыва SSH и после перезагрузки.
- **Генерация юнита утилитой (BREAKING).** Каталог `systemd/` в деплоящем проекте больше не читается и не передаётся. Юнит формируется на хосте по шаблону, единственный каноничный запуск — `ExecStart=/usr/bin/npm start`, `WorkingDirectory=<project>/current`.
- **Верификация после запуска.** Успех деплоя определяется состоянием службы, а не фактом доставки файлов: ожидание `active` и (при известном порту) прослушивания порта с щедрым таймаутом под Pi Zero. Иначе — ненулевой код возврата, откат `current` на предыдущий релиз, без `🎉`.
- **Атомарность удалённой цепочки.** Шаги выполняются отдельными вызовами с проверкой кода возврата каждого; `|| true` остаётся только внутри изолированного шага и не может обнулить код возврата предыдущих шагов.
- **Исправление `ps` для user-юнитов.** Имя службы из `/proc/<pid>/cgroup` берётся последним совпадением (`tail -n1`), иначе для user-юнита возвращается `user@1000.service`.
- **Очистка неканоничного наследия на хосте.** Разовое удаление system-юнитов, релизов и каталогов проектов, созданных прежними инструментами (детальный список и границы — в design.md).

## Capabilities

### New Capabilities

- `user-unit-runtime`: Развёртывание и обслуживание служб через user-менеджер systemd без привилегий root: включение linger, генерация unit-файла по каноничному шаблону запуска, установка в каталог пользователя, включение автозапуска и верификация фактической работоспособности службы.

### Modified Capabilities

- `deploy-pipeline`: Установка службы выполняется генерированным user-юнитом вместо копирования `systemd/<service>` в `/etc/systemd/system`; шаги конвейера проверяются по коду возврата individually; успех деплоя требует подтверждённой активной службы.
- `service-lifecycle`: `stop` и `disable` выполняются через `systemctl --user` без `sudo`; разрешение имён службы учитывает user-описание.
- `service-discovery`: Имя службы systemd определяется по последнему сегменту cgroup; таблица различает «не задеплоен», «задеплоен, но не запущен» и «запущен».

## Impact

- **Код:** `src/index.ts` — конвейер деплоя, `handlePs`, `handleServiceControl`, строка `usage`.
- **Целевой хост:** `~/.config/systemd/user/` становится домом юнитов; `/etc/systemd/system/*.service` для деплоящихся проектов более не используется.
- **Деплоящиеся проекты:** каталог `systemd/` и поле `pizdeploy.service` теряют смысл; появляется необязательное `pizdeploy.port` для проверки прослушивания.
- **Тесты:** `test/cli.test.ts` — заглушки `ssh`/`scp` должны покрывать user-команды, отказ верификации и отсутствие маскирующего `|| true`.
- **Документация:** `README.md` — новый конвейер, отсутствие `sudo`, linger, канон `npm start`.
- **Риск:** смена менеджера юнитов несовместима с уже установленными system-юнитами — требуется разовая миграция/очистка.
