# Design

## Context

Проект `pizdeploy` («pi zero deploy») представляет собой CLI-утилиту на рантайме Bun для zero-privilege деплоя Node.js-приложений на Raspberry Pi.

В ходе аудита безопасности и качества кодовой базы перед публикацией было установлено:

1. **Учетные данные и секреты**: В истории git и файлах проекта отсутствуют реальные пароли, приватные SSH-ключи, токены или реальные сетевые IP-адреса (найдены только демонстрационные токены-заглушки в README и тестах).
2. **Уязвимости инъекций**: Входные параметры (`name`, `service`, `host`) подставляются в строки удаленных shell-команд без строгой валидации. Вставка содержимого unit-файла выполняется через heredoc (`cat <<'PIZDEPLOY_UNIT'`), что уязвимо к разрыву маркера.
3. **Захардкоженные пути**: Путь `/home/pi/projects` жестко прописан в константах, генераторе systemd-юнитов и скрипте инспекции `ps`. Начиная с 2022 года дистрибутивы Raspberry Pi OS (Bullseye/Bookworm) не создают пользователя `pi` по умолчанию, что делает утилиту неработоспособной для пользователей с иными логинами (`ubuntu`, `dietpi`, `admin` и др.).
4. **Архитектура кодовой базы**: Весь исходный код сосредоточен в одном монолитном файле `src/index.ts` объемом около 1000 строк.
5. **CLI UX**: Запрос `--help` или `--version` завершается кодом ошибки 2, а в корне проекта присутствует устаревший файл `systemd/app.service`.

## Goals / Non-Goals

**Goals:**

- Полное устранение рисков Shell/Command Injection и SSH Argument Injection за счет белых списков валидации и безопасной передачи данных.
- Поддержка произвольных пользователей на Raspberry Pi: замена хардкода `/home/pi` на динамическое использование переменной `$HOME` в удаленных скриптах и спецификатора `%h` в unit-файлах systemd.
- Безопасная запись файлов юнита на удаленный хост (передача через Base64 или stdin) и изоляция локального архива сборки во временном каталоге ОС (`tmpdir`).
- Модульный рефакторинг `src/`: разделение на чистые специализированные модули (`cli`, `config`, `ssh`, `unit`, `service`, `ps`, `deploy`) с сохранением полной обратной совместимости и прохождением всех существующих тестов.
- Реализация стандартных флагов `--help` (`-h`) и `--version` (`-v`) с кодом 0.
- Удаление устаревших артефактов (`systemd/app.service`), исправление опечаток в `my-app`, обновление `package.json`.
- Подготовка актуального `README.md` с названием **pi zero deploy**, именем утилиты `pizdeploy` и разделом рекомендаций по безопасности.

**Non-Goals:**

- Отказ от системных клиентов OpenSSH (`ssh`, `scp`) в пользу JS-библиотек (OpenSSH обеспечивает прозрачную интеграцию с `~/.ssh/config`, `ProxyJump` и ssh-agent).
- Внедрение привилегированных команд (`sudo`, системные каталоги `/etc/systemd`).

## Decisions

### 1. Валидация входных данных и экранирование

- Имя проекта (`name`) и имя службы (`service`): валидация регулярным выражением `/^[a-zA-Z0-9_\-\.]+$/`. При нарушении — прерывание с ошибкой валидации до исполнения каких-либо shell-команд.
- Адрес хоста (`host`): запрет ведущих дефисов (`/^-/`) для предотвращения внедрения параметров OpenSSH (например, `-oProxyCommand=...`).
- Порт (`port`): строгая проверка диапазона целых чисел `1..65535`.

### 2. Динамический домашний каталог пользователя на хосте

- В шаблонах systemd-юнитов: использование стандартного спецификатора systemd `%h` (User Home Directory), например:
  `WorkingDirectory=%h/projects/${name}/current`.
  Это штатный механизм systemd для пользовательских юнитов, который автоматически раскрывается в домашнюю директорию текущего пользователя.
- В удаленных shell-командах: использование переменной окружения `${HOME}` и тильды `~/projects`. В `buildPsScript` сканирование выполняется по `"$HOME/projects"/*` вместо фиксированного `/home/pi/projects/*`.

### 3. Безопасная передача unit-файла на хост

- Вместо строкового heredoc с риском коллизии маркера:
  `cat > ${unitDir}/${service} <<'PIZDEPLOY_UNIT' ...`
  использовать кодирование содержимого в Base64:
  `echo "${Buffer.from(unit).toString('base64')}" | base64 -d > "${unitDir}/${service}"`.
  Это гарантирует целостность файла при любых спецсимволах, кавычках, долларах и переводах строк.

### 4. Изоляция локального архива

- Создание архива не в рабочей директории `./dist.tar.gz`, а во временном каталоге ОС (`import { tmpdir } from 'node:os'`) с уникальным именем: `join(tmpdir(), \`pizdeploy-\${Date.now()}-\${randomId}.tar.gz\`)`.
- Гарантированное удаление в блоке `finally`. Это защищает файлы разработчика от случайной перезаписи.

### 5. Модульная структура исходного кода

Разбиение `src/index.ts` на подмодули:

- `src/types.ts`: общие типы (`RemoteResult`, `AutobuildInfo`, `ServiceAction`, etc.).
- `src/cli.ts`: разбор аргументов, генерация справки `--help`, отображение `--version`, валидация.
- `src/config.ts`: чтение `package.json`, нормализация адреса хоста, имени сервиса и порта.
- `src/ssh.ts`: опции SSH/SCP, `remoteExec`, управление мультиплексированием `ControlMaster`.
- `src/unit.ts`: разбор и генерация unit-файла (`renderUnit`), команда `handleInit`.
- `src/service.ts`: команды жизненного цикла службы (`handleServiceControl`).
- `src/ps.ts`: скрипт инспекции (`buildPsScript`) и вывод таблицы (`handlePs`).
- `src/deploy.ts`: шаги сборки, архивации, доставки, переключения симлинков, linger и верификации (`verifyService`).
- `src/index.ts`: точка входа, экспорт публичного API для тестов и запуск `main()`.

### 6. Очистка репозитория и README

- Удалить мертвый каталог `systemd/app.service`.
- Исправить в `my-app/systemd-unit.service` строку `Environment="NODE_MODULES=production"` на `Environment="NODE_ENV=production"`.
- Обновить `README.md`:
  - Заголовок: `# pi zero deploy (pizdeploy)`.
  - Уточнить, что Raspberry Pi может использовать любого пользователя (не обязательно `pi`).
  - Описать правила безопасности: хранение секретов в `systemd-unit.service` локально, добавление его в `.gitignore` при наличии реальных паролей/токенов бота, отсутствие sudo.

## Risks / Trade-offs

- **[Спецификатор `%h` в старых версиях systemd]** → `%h` поддерживается в systemd начиная с версии 200 (более 10 лет, присутствует во всех версиях Raspberry Pi OS / Debian).
- **[Обратная совместимость тестов]** → В существующих тестах моки ssh проверяют конкретные строки вызовов (например, `WorkingDirectory=/home/pi/projects/...` или `systemctl --user stop`).
  _Митигация:_ При обновлении логики адаптировать фикстуры и тесты так, чтобы они проверяли безопасные эквиваленты (`%h/projects/...` или динамические переменные), сохранив 100% покрытие.
