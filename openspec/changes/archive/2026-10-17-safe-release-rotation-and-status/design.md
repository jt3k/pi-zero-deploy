# Design

## Context

Конвейер развёртывания `pizdeploy` выполняет атомарный деплой: сборка, передача архива в `incoming/`, распаковка в `releases/<name>_<hash5>`, переключение симлинка `current`, запуск/рестарт службы и верификация. Завершающим шагом конвейера (шаг 14) является ротация директории `releases/`.

В текущей реализации:

```bash
cd ${releasesDir} && ls -1d * 2>/dev/null | sort | head -n -3 | xargs rm -rf 2>/dev/null || true
```

Здесь присутствуют две архитектурные уязвимости:

1. `sort` выполняет лексикографическую сортировку по строке хэша SHA-256. Так как хэш распределён случайно, свежеразвёрнутый релиз может оказаться лексикографически первым и быть удалён сразу после успешной активации.
2. Отсутствует проверка симлинка `current`. Ротация способна удалить релиз, на который ссылается `current`, оставляя «висячий» симлинк. При первом же падении приложения или перезагрузке systemd не может войти в рабочую директорию (`WorkingDirectory=%h/projects/<name>/current`) и переходит в циклическую ошибку `200/CHDIR`.
3. Команда `pizdeploy ps` при опросе systemd (`ActiveState`) проверяет только равенство `astate == "active"`, относя состояния `activating` (включая подсостояние `auto-restart`) и `failed` к `inactive`, скрывая факт сбоя или циклического перезапуска.

## Goals / Non-Goals

**Goals:**

- Обеспечить строгий инвариант: каталог, на который указывает `${projectDir}/current`, никогда не удаляется при ротации.
- Реализовать сортировку релизов по времени изменения (`mtime`, новейшие первыми) и сохранять как минимум 3 самых свежих релиза.
- Различать в `pizdeploy ps` состояния `running`, `restarting` (`activating`), `failed` и `inactive`.
- Вынести удалённую команду ротации в отдельную тестируемую функцию-генератор в `src/deploy.ts`.

**Non-Goals:**

- Изменение структуры именования релизов (`<name>_<hash5>`).
- Изменение поведения самого systemd или значений директив `Restart=`/`RestartSec=`.

## Decisions

### 1. Алгоритм безопасной ротации релизов на удалённом хосте

**Выбранное решение:**
Формировать bash-команду ротации, которая:

1. Определяет канонический путь текущего активного релиза:
   `cur=$(readlink -f "${currentLink}" 2>/dev/null || true)`
2. Переходит в директорию `releases/` и получает список директорий, отсортированных по `mtime` (новые первыми): `ls -1td */ 2>/dev/null`.
3. Пропускает 3 самых свежих релиза через `tail -n +4`.
4. Для каждого кандидата на удаление проверяет равенство канонического пути с `$cur`. Если путь совпадает с активным релизом — кандидат пропускается.
5. Удаляет только подтверждённые неактивные старые релизы.

```bash
cur=$(readlink -f "${currentLink}" 2>/dev/null || true)
cd "${releasesDir}" 2>/dev/null && \
for d in $(ls -1td */ 2>/dev/null | tail -n +4); do
  full=$(readlink -f "$d" 2>/dev/null || true)
  if [[ -n "$cur" && "$full" == "$cur" ]]; then
    continue
  fi
  rm -rf "$d"
done || true
```

**Альтернативы:**

- _Добавление таймстемпа в имя релиза (`<name>_<timestamp>_<hash5>`)_: Изменяет формат идентификаторов релиза в `ps`, требует изменений в регулярных выражениях и документации. Отклонено в пользу прозрачной сортировки по `mtime`.
- _Использование `find ... -mtime`_: Сложнее экранировать и требует учёта особенностей версий find на разных дистрибутивах Linux. Конструкция `ls -1td */` стандартна и работает во всех окружениях.

### 2. Дифференциация статусов в `pizdeploy ps`

**Выбранное решение:**
В скрипте `buildPsScript` ([src/ps.ts](file:///Users/jt3k/work/pizdeploy/src/ps.ts)) расширить обработку `ActiveState`:

- `astate == "active"` и `MainPID > 0` → `stat="running"`, `m_pid="$main_pid"`.
- `astate == "activating"` → `stat="restarting"`, `m_pid="null"`.
- `astate == "failed"` → `stat="failed"`, `m_pid="null"`.
- Все остальные случаи (или `astate == "inactive"`) → `stat="inactive"`.

В `handlePs` значение поля `status` выводится в колонку `Status` без изменений.

**Альтернативы:**

- _Опрос journalctl на каждый сервис в `ps`_: Создаёт избыточный сетевой RTT и замедляет выполнение на слабых одноплатных ПК (Raspberry Pi Zero). `systemctl show` возвращает необходимые свойства мгновенно.

## Risks / Trade-offs

- **[Риск] `ls -1td` зависит от системного времени (mtime)**: Если системные часы на Raspberry Pi сбиты (например, при загрузке без RTC до синхронизации NTP), mtime может быть искажён.
  → _Митигация_: Проверка `$cur` защищает активный релиз независимо от системного времени. Даже если mtime исказился, текущий релиз никогда не будет удалён.

- **[Риск] Влияние новых статусов на сторонние скрипты**: Скрипты, ожидавшие только `running` или `inactive`, увидят `restarting` или `failed`.
  → _Митигация_: `restarting` и `failed` точнее отражают реальность и позволяют автоматизации диагностировать проблемы вместо ложного ожидания остановленной службы.
