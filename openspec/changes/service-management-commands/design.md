# Design

## Context

В текущей версии `pizdeploy` (см. `proposal.md`):
- Доступны подкоманды `deploy` (по умолчанию), `ps`, `stop` и `disable`.
- Управление службами реализовано в функции `handleServiceControl(host, action, service)`, которая выполняет SSH-команду `systemctl --user <action> <service>`.
- Сбор данных для `pizdeploy ps` происходит в bash-скрипте, формируемом функцией `buildPsScript()`. Он обходит все папки `/home/pi/projects/*`, независимо от наличия симлинка `current`.

## Goals / Non-Goals

**Goals:**
- Расширить CLI стандартизированными сервисными командами (`start`, `restart`, `status`, `logs`, `remove`/`rm`).
- Реализовать для `remove`: остановку, отключение, удаление unit-файла, `systemctl --user daemon-reload` и удаление симлинка `current`.
- Обновить фильтрацию в `buildPsScript`: не отображать папки в таблице `ps`, если у них нет ни симлинка `current`, ни активного слушающего процесса.
- Сохранить обратную совместимость с имеющимся парсером флагов и аргументов.

**Non-Goals:**
- Удаление фактических файлов релизов `/home/pi/projects/<name>/releases/` при вызове `remove` (пользователь сохраняет возможность вернуть или вручную очистить историю).
- Добавление интерактивного стриминга логов с удержанием сессии (`journalctl -f`) в фоновом режиме без блокировки — для первой версии достаточно вывод последних N строк (`journalctl --user -u <service> -n 50 --no-pager`).

## Decisions

### 1. Соответствие стандартам именования команд
- Выбраны каноничные глаголы: `start`, `stop`, `restart`, `status`, `logs`, `disable`, `remove` (с общепринятым алиасом `rm`).
- Альтернативы: `kill`, `down`, `destroy`, `off`. Отклонены, так как `start`/`stop`/`restart`/`status`/`logs`/`remove` являются общепринятыми стандартами в Docker, systemd, PM2 и CLI-инструментах управления сервисами.

### 2. Реализация команды `remove` / `rm`
- Команда `remove` выполняет удалённую составную команду:
  ```bash
  systemctl --user stop <service> 2>/dev/null || true
  systemctl --user disable <service> 2>/dev/null || true
  rm -f ~/.config/systemd/user/<service>
  systemctl --user daemon-reload
  rm -f /home/pi/projects/<name>/current
  ```
- Это гарантирует, что служба полностью выгружена из памяти и автозапуска, unit-файл удалён, а симлинк `current` снят. Директория `/home/pi/projects/<name>/releases` намеренно остаётся нетронутой.

### 3. Фильтрация проектов в `pizdeploy ps`
- В `buildPsScript` условие добавления в список обновляется: проект попадает в JSON-массив только если:
  - Существует симлинк `current`: `[[ -L "$p/current" ]]` ИЛИ
  - Найден активный запущенный процесс: `[[ "$stat" == "running" ]]`.
- Если оба условия ложны (например, после `remove`, когда `current` удалён и процесс остановлен), директория пропускается и не засоряет таблицу.

### 4. Парсинг CLI аргументов
- Парсер аргументов в `main()` расширяется списком:
  ```ts
  const SERVICE_CMDS = ["stop", "disable", "start", "restart", "status", "logs", "remove", "rm"];
  ```
- Для `status` и `logs` вывод удалённой команды транслируется непосредственно в stdout пользователя.

## Risks / Trade-offs

- **[Риск]** Попытка вызвать `start` для службы, которая была удалена (`remove`).
  → *Митигация:* `systemctl --user start` вернёт ошибку `Unit not found`, утилита выведет понятное сообщение в консоль и завершится с кодом 1.
- **[Риск]** Удаление `current` оставляет проект в `/home/pi/projects/` как пустой каталог релизов.
  → *Митигация:* Это безопасное поведение, предотвращающее случайную потерю данных; при желании пользователь может выполнить `rm -rf` на хосте.
