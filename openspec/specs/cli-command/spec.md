# cli-command Specification

## Purpose
Определяет наблюдаемое поведение консольной команды `pizdeploy`: как она становится доступной в терминале пользователя, что выводит при успешном запуске и как ведёт себя при отсутствии необходимого рантайма.

## Requirements

### Requirement: Команда доступна в PATH

Система SHALL предоставлять исполняемую команду с именем `pizdeploy`, доступную в интерактивной оболочке пользователя (macOS, zsh или bash) после выполнения документированной установки из каталога проекта.

#### Scenario: Команда найдена после установки

- **WHEN** пользователь выполнил установку утилиты и в новой сессии терминала вводит `pizdeploy`
- **THEN** оболочка находит команду (выход `which pizdeploy` непустой) и запускает её без указания пути к проекту

#### Scenario: Установка без аргументов не требует прав root

- **WHEN** пользователь устанавливает команду из обычного пользовательского аккаунта macOS
- **THEN** установка завершается успешно без использования `sudo` и записи в системные каталоги

### Requirement: Поведение не зависит от текущего каталога

Система SHALL запускаться одинаково независимо от того, запущена ли она внутри каталога проекта: точка входа находит исполняемый код по своему реальному пути, а не по каталогу вызова.

#### Scenario: Запуск вне каталога проекта
- **WHEN** пользователь выполняет `pizdeploy` из произвольного каталога, например из домашней директории
- **THEN** утилита запускается и доходит до выполнения удалённой команды
- **AND** код возврата определяется результатом этой команды, а не каталогом вызова

### Requirement: Флаг --ssh задаёт адрес подключения

Система SHALL принимать флаг `--ssh <user@host>` в любом месте аргументов командной строки, в том числе в форме `--ssh=<user@host>`, и передавать его значение как адрес подключения.

#### Scenario: Флаг со значением через пробел
- **WHEN** пользователь выполняет `pizdeploy --ssh pi@other.local`
- **THEN** адресом подключения становится `pi@other.local`

#### Scenario: Флаг со значением через знак равенства
- **WHEN** пользователь выполняет `pizdeploy --ssh=pi@other.local`
- **THEN** адресом подключения становится `pi@other.local`

### Requirement: Ошибки использования завершаются кодом 2

Система SHALL завершаться с кодом возврата 2 и сообщением в stderr, содержащим актуальную подсказку по использованию `usage: pizdeploy [ps|stop|disable] [name] [--ssh <user@host>] [--dry-run]`, при неизвестном аргументе или отсутствии обязательного значения после флага `--ssh`.

#### Scenario: Неизвестный аргумент
- **WHEN** пользователь выполняет `pizdeploy --help` или `pizdeploy restart app`
- **THEN** в stderr появляется сообщение, содержащее `usage: pizdeploy [ps|stop|disable] [name] [--ssh <user@host>] [--dry-run]`
- **AND** stdout пуст
- **AND** код возврата равен 2

#### Scenario: --ssh без значения
- **WHEN** пользователь выполняет `pizdeploy --ssh` или `pizdeploy stop --ssh`
- **THEN** в stderr появляется сообщение, содержащее `usage: pizdeploy [ps|stop|disable] [name] [--ssh <user@host>] [--dry-run]`
- **AND** stdout пуст
- **AND** код возврата равен 2

### Requirement: Исполнение опирается на возможности Bun

Система SHALL выполнять логику утилиты через рантайм Bun с шебангом `#!/usr/bin/env bun` и опираться на его встроенные возможности (Bun Shell `$`, `Bun.which`, стандартный парсер аргументов, чтение JSON), избегая внешних npm-пакетов и написания собственных велосипедов.

#### Scenario: Запуск через рантайм Bun
- **WHEN** пользователь выполняет `pizdeploy`
- **THEN** выполнение происходит в среде рантайма Bun с использованием его встроенных API

### Requirement: Подкоманда ps для инспекции состояния

Система SHALL поддерживать подкоманду `ps` (`pizdeploy ps`), запускающую опрос статуса удалённых сервисов без выполнения сборки проекта, создания архива и операций деплоя.

#### Scenario: Запуск команды pizdeploy ps
- **WHEN** пользователь выполняет `pizdeploy ps`
- **THEN** утилита не выполняет локальную сборку `bun run build`
- **AND** не создает архив `dist.tar.gz`
- **AND** выполняет запрос инспекции статуса сервисов на удалённом хосте

### Requirement: Подкоманды stop и disable

Система SHALL поддерживать подкоманды `stop` и `disable` с опциональным позиционным аргументом имени службы или проекта (`pizdeploy stop [name]` и `pizdeploy disable [name]`), выполняющие управление службой на удалённом хосте без выполнения сборки и деплоя.

#### Scenario: Запуск pizdeploy stop
- **WHEN** пользователь выполняет `pizdeploy stop` или `pizdeploy stop my-app`
- **THEN** утилита не запускает `bun run build` и не создает архив
- **AND** передает команду остановки соответствующей службы на удалённый хост

#### Scenario: Запуск pizdeploy disable
- **WHEN** пользователь выполняет `pizdeploy disable` или `pizdeploy disable my-app`
- **THEN** утилита не запускает `bun run build` и не создает архив
- **AND** передает команду отключения автозапуска службы на удалённый хост
