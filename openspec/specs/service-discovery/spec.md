# service-discovery Specification

## Purpose
Обеспечивает обнаружение и инспекцию состояния всех сервисов, развёрнутых на удалённом сервере, их активных релизов, привязанных служб systemd, открытых портов и генерацию кликабельных URL.

## Requirements

### Requirement: Обнаружение задеплоенных проектов и активных релизов

Система SHALL сканировать удалённую директорию `/home/pi/projects/*`, определять имя каждого задеплоенного проекта и вычислять его текущий активный релиз на основе таргета симлинка `current`.

#### Scenario: Определение активного релиза
- **WHEN** выполняется инспекция проектов
- **THEN** для каждого каталога в `/home/pi/projects/*` определяется имя проекта
- **AND** считывается значение симлинка `current` для получения идентификатора релиза (например, `<name>_<hash>`)
- **AND** если симлинк отсутствует или повреждён, релиз помечается как отсутствующий (`-`)

### Requirement: Сбор активных слушающих процессов и служб systemd

Система SHALL анализировать слушающие сокеты через `ss -tlpn`, строго сопоставлять PID процессов с границами рабочей директории проектов (`cwd == project_dir` или `cwd` начинается с `project_dir/`), исключая ложное срабатывание для проектов с префиксными именами, и определять имя службы systemd через `/proc/<pid>/cgroup` без использования прав суперпользователя `sudo`.

#### Scenario: Сопоставление запущенного процесса с проектом
- **WHEN** процесс слушает входящие соединения на локальном порту
- **AND** его рабочая директория `/proc/<pid>/cwd` совпадает с каталогом проекта `/home/pi/projects/<name>` или является его поддиректорией
- **THEN** статус проекта помечается как `running`
- **AND** фиксируются его сетевой порт, идентификатор процесса PID и имя службы systemd из cgroup

#### Scenario: Изоляция проектов с похожими префиксами имён
- **WHEN** в `/home/pi/projects` существуют проекты с префиксными именами (например, `app` и `app-worker`)
- **AND** запущен процесс, чей рабочий каталог находится внутри `app-worker`
- **THEN** проект `app` не сопоставляется с этим процессом и не перехватывает его статус

#### Scenario: Проект не запущен
- **WHEN** ни один слушающий процесс не имеет рабочей директории внутри проекта
- **THEN** статус проекта помечается как `inactive`
- **AND** порт, PID и служба помечаются как отсутствующие (`-`)

### Requirement: Форматирование таблицы статусов и кликабельных ссылок

Система SHALL выводить собранную информацию в терминал в виде структурированной таблицы через встроенный API Bun `console.table()`, автоматически формируя кликабельные веб-ссылки `http://<host>:<port>` для активных сервисов.

#### Scenario: Отображение таблицы статуса
- **WHEN** завершён сбор данных с удалённого сервера
- **THEN** формируется таблица со столбцами `Project`, `Release`, `Status`, `URL`, `Service`, `PID`
- **AND** для запущенных проектов со слушающим портом формируется ссылка вида `http://<host>:<port>`
- **AND** таблица выводится в консоль стандартным методом `console.table()`
