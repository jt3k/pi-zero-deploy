# user-unit-runtime Specification

## Purpose

Определяет развёртывание и обслуживание служб через пользовательский менеджер systemd на целевом хосте: включение автозапуска сессии пользователя, генерацию unit-файла по каноничному шаблону и подтверждение фактической работоспособности службы без использования привилегий суперпользователя.

## Requirements

### Requirement: Службы разворачиваются без привилегий суперпользователя

Система SHALL выполнять все операции с службами на целевом хосте от имени подключаемого пользователя без вызова `sudo` и без записи в системные каталоги.

#### Scenario: Ни одна команда деплоя не требует sudo

- **WHEN** выполняется деплой, остановка или отключение автозапуска службы
- **THEN** ни одна удалённая команда не содержит `sudo`
- **AND** ни одна удалённая команда не обращается на запись в `/etc/systemd/system`

#### Scenario: Хост не разрешает привилегированные операции

- **WHEN** на целевом хосте `sudo` требует пароль
- **THEN** операция завершается успешно
- **AND** служба оказывается запущенной

### Requirement: Автозапуск пользовательской сессии включается до установки службы

Система SHALL перед первой установкой службы убедиться, что для подключаемого пользователя включён режим автозапуска пользовательской сессии (`linger`), и включить его, если он выключен.

#### Scenario: Linger выключен

- **WHEN** для подключаемого пользователя автозапуск сессии выключен
- **THEN** система включает его командой `loginctl enable-linger` для этого пользователя
- **AND** убеждается, что состояние переключилось на включённый
- **AND** служба продолжает работать после закрытия SSH-сессии

#### Scenario: Linger уже включён

- **WHEN** автозапуск сессии уже включён
- **THEN** система не изменяет это состояние и не считает его ошибкой

### Requirement: Unit-файл формируется утилитой по каноничному шаблону

Система SHALL формировать unit-файл на основе файла шаблона `systemd-unit.service` (из корня деплоящего проекта при его наличии или эталонного шаблона `pizdeploy`), автоматически внедрять в секцию `[Service]` параметры `WorkingDirectory` (путь к `current`) и `ExecStart` (команда из `scripts.start`), сохранять пользовательские переменные окружения и директивы, использовать `NODE_ENV=production` по умолчанию, и записывать юнит в `~/.config/systemd/user/<service>.service` строго под именем целевой службы. Если в секции `[Service]` не задана директива `Restart=`, система SHALL автоматически внедрять `Restart=always`. Если не задана директива `RestartSec=`, система SHALL автоматически внедрять `RestartSec=2`. Если эти директивы явно заданы пользователем в шаблоне, система SHALL сохранять их без изменений.

#### Scenario: Юнит создаётся для нового проекта
- **WHEN** деплоится проект с корректно заданным `scripts.start`
- **THEN** в каталоге пользовательских юнитов создаётся файл `<service>`
- **AND** его `WorkingDirectory` указывает на симлинк `current` каталога проекта
- **AND** его `ExecStart` запускает команду, полученную из `scripts.start`
- **AND** заданы перезапуск при падении, автозапуск при старте пользовательской сессии и `Environment="NODE_ENV=production"`

#### Scenario: Локальный каталог systemd игнорируется
- **WHEN** в деплоящем проекте присутствует каталог `systemd/` с произвольным содержимым
- **THEN** это содержимое не передаётся на хост и не влияет на установленный юнит

#### Scenario: Использование пользовательского шаблона systemd-unit.service
- **WHEN** в корне деплоящего проекта присутствует файл `systemd-unit.service`
- **THEN** утилита использует его в качестве основы, сохраняя пользовательские директивы (например, `Environment=`)
- **AND** автоматически внедряет актуальные `WorkingDirectory` и `ExecStart`
- **AND** передаёт и сохраняет юнит на хосте под каноничным именем `<service>.service`

#### Scenario: Использование дефолтного шаблона pizdeploy
- **WHEN** в корне деплоящего проекта отсутствует файл `systemd-unit.service`
- **THEN** утилита использует эталонный шаблон `systemd-unit.service` из репозитория `pizdeploy`
- **AND** передаёт и сохраняет его на хосте под каноничным именем `<service>.service`

#### Scenario: Автоматическое добавление Restart=always и RestartSec=2 при их отсутствии в кастомном шаблоне
- **WHEN** в корне проекта задан файл `systemd-unit.service`
- **AND** в секции `[Service]` отсутствуют строки `Restart=` и `RestartSec=`
- **THEN** сгенерированный юнит содержит `Restart=always` и `RestartSec=2`

#### Scenario: Сохранение явных настроек Restart и RestartSec из шаблона
- **WHEN** в файле `systemd-unit.service` явно указаны `Restart=on-failure` и `RestartSec=5`
- **THEN** сгенерированный юнит сохраняет `Restart=on-failure` и `RestartSec=5` без замены на дефолты

### Requirement: Единственный каноничный способ запуска приложения

Система SHALL требовать наличия команды запуска в поле `scripts.start` файла `package.json` проекта. Система SHALL прерывать деплой с ошибкой, если скрипт `start` отсутствует или пуст. При наличии пользовательского `scripts.build` система SHALL адаптировать путь из `scripts.start`, удаляя префикс `dist/`. При срабатывании автоматического билда (когда `scripts.build` отсутствует) команда запуска в `ExecStart` SHALL автоматически указывать на сгенерированный ESM-бандл `/usr/bin/node <имя>.mjs` с сохранением дополнительных параметров Node.js, если они были указаны в `scripts.start`.

#### Scenario: Артефакт сборки назван произвольно при наличии build
- **WHEN** в `package.json` задан `scripts.build` и он создаёт артефакт
- **AND** скрипт `start` в `package.json` проекта запускает его
- **THEN** служба запускается успешно без каких-либо настроек имени файла в утилите

#### Scenario: Адаптация ExecStart при автобилде
- **WHEN** скрипт `build` в `package.json` отсутствует
- **AND** в `scripts.start` указано `node ./src/app.js`
- **THEN** автобилд создаёт `./dist/app.mjs`
- **AND** сгенерированный юнит содержит `ExecStart=/usr/bin/node app.mjs`

#### Scenario: Сохранение флагов Node.js при автобилде
- **WHEN** скрипт `build` отсутствует
- **AND** в `scripts.start` указано `node --expose-gc ./server.js`
- **THEN** автобилд создаёт `./dist/server.mjs`
- **AND** сгенерированный юнит содержит `ExecStart=/usr/bin/node --expose-gc server.mjs`

#### Scenario: В релизе нет скрипта start
- **WHEN** в `package.json` проекта отсутствует скрипт `start`
- **THEN** деплой завершается с ненулевым кодом возврата и понятным сообщением об ошибке еще до сборки и передачи файлов на хост

#### Scenario: Скрипт start задан корректно
- **WHEN** в `package.json` присутствует непустой скрипт `scripts.start` (например, `node index.js`)
- **THEN** деплой продолжается и команда используется в `ExecStart` службы

#### Scenario: Скрипт start отсутствует в package.json
- **WHEN** в `package.json` отсутствует поле `scripts.start` или секция `scripts`
- **THEN** деплой немедленно прерывается с ненулевым кодом ошибки
- **AND** в stderr выводится понятное сообщение о непригодности проекта для деплоя
- **AND** передача файлов на хост не выполняется

#### Scenario: Скрипт start пустой
- **WHEN** в `package.json` поле `scripts.start` является пустой строкой или строкой из пробелов
- **THEN** деплой прерывается с ошибкой до выполнения сборки и сетевых вызовов

### Requirement: Успех деплоя подтверждается состоянием службы

Система SHALL считать деплой успешным только после подтверждения того, что служба перешла в состояние `active` в пределах оптимизированного таймаута (до 60 секунд) с шагом опроса в 1 секунду (настраиваемым через `PIZDEPLOY_VERIFY_INTERVAL_MS`), и завершать деплой с ненулевым кодом возврата, если подтверждение не получено. Для служб без указанного порта стабильность запуска SHALL проверяться выдержкой отсутствия перезапусков в 5 секунд (настраиваемой через `PIZDEPLOY_STABLE_HOLD_MS`). При успехе система SHALL выводить краткое подтверждение с идентификатором релиза, опуская избыточные технические сведения об имени службы и хосте.

#### Scenario: Служба активна
- **WHEN** после установки юнита служба переходит в состояние `active` в пределах отведённого времени ожидания
- **THEN** деплой завершается кодом 0
- **AND** в stdout выводится заголовок успешного развертывания релиза с его идентификатором
- **AND** отдельная строка с именем systemd-службы не выводится

#### Scenario: Служба не становится активной
- **WHEN** служба не переходит в состояние `active` в пределах отведённого времени ожидания
- **THEN** деплой завершается ненулевым кодом возврата
- **AND** сообщение об успехе не выводится
- **AND** симлинк `current` возвращается на предыдущий релиз, если он существовал

#### Scenario: Быстрая фиксация стабильности для службы без порта
- **WHEN** служба без указанного порта переходит в состояние `active` и не перезапускается в течение 5 секунд
- **THEN** деплой завершается успешно без лишней задержки

#### Scenario: Медленный запуск на слабом железе
- **WHEN** служба переходит в `active` дольше нескольких десятков секунд
- **THEN** система ожидает в пределах увеличенного таймаута и не считает такой запуск ошибкой

### Requirement: Порт приложения проверяется при его известности

Система SHALL дополнительно проверять прослушивание порта приложением, если порт задан в конфигурации проекта, и учитывать его недоступность как неуспех деплоя. При успешном развертывании URL выводится только если порт задан; если порт не задан, сообщение о пропуске проверки не выводится.

#### Scenario: Порт задан и слушается

- **WHEN** в конфигурации проекта задан порт и после запуска служба слушает этот порт
- **THEN** деплой завершается кодом 0
- **AND** в stdout выводится URL приложения

#### Scenario: Порт задан, но не слушается

- **WHEN** порт задан, но по истечении таймаута его никто не слушает
- **THEN** деплой завершается ненулевым кодом возврата
- **AND** выводится различимое сообщение о причине

#### Scenario: Порт не задан

- **WHEN** порт в конфигурации проекта не задан
- **THEN** проверка порта пропускается и успех определяется только состоянием службы
- **AND** сообщение о пропуске проверки порта не выводится в stdout
